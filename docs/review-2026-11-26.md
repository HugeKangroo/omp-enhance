# omp-enhance 交互、架构与交付评审

2026-11-26，基线为本地 `24107a4` 加当时工作区尚未提交的角色工作流改动，环境为 Bun 1.4.0、OMP 19.1.1。以下九项是这一基线上的评审发现。每项的验收条件可直接用于设计回归测试。

修复进展、复核中仍能触发的问题和回归标准见[修复后复核](#修复后复核)。

## 项目目标与执行路径

用户在一个 OMP 窗口里通过 `/coord` 管理多个项目，用自然语言交代目标、回答业务问题、接收交付。总控选择目标目录和专员，插件根据 YAML 角色约束创建 OMP 子会话。专员提交带证据的交接结果，Flow 决定继续、返修或挂起。SQLite 保存各项目的任务、交接和检查点，`/flow` 展示进度。[使用示例](../README.md) · [架构说明](architecture.md)

建议保留前台总控与后台执行的分工，以及角色规则与项目知识的分工。用户需要能从记录里看清一次答复批准了哪件事、任务完成后去哪里取结果，以及 QA 实际验证了哪个版本。

## 交互与派单

### 1. 一条答复放行了两个独立问题

两个并行的人工节点分别询问是否批准 backend 和 billing。系统只报告了 backend。答复“只同意 backend，billing 另等决定”后，两节点都变成 `succeeded`，记录里都写了“已确认放行”。调度器只展示首个待答问题，恢复入口没有指定节点，状态机随后遍历了所有待答节点。前台 `algo` 停在 `align_metric` 时，开始下一轮对话就会触发 `baseline`。[问题汇总](../src/flow/machine-helpers.ts#L204) · [后台恢复](../src/flow/machine.ts#L84) · [前台推进](../src/omp/workflow-fg.ts#L61)

**建议与验收**　让总控列出待答问题，后台将答复绑定到对应的 `flowId` 和 `nodeId`，并保存用户原话。重复上述答复后，只有 backend 可以继续，billing 仍为 `waiting_input`。前台只问“现在进度如何”时，指标确认阶段保持挂起。

### 2. 工具参数定义阻断了合法 DAG

在实际 OMP 宿主上校验注册参数，`roles: ["dev", "qa"]` 通过。提交含 `id`、`kind`、`role` 的合法 planner 节点时，这三个字段都被要求删除。补丁的 `skipNodeIds` 也被拒绝。注册代码把节点和补丁声明成禁止额外字段的空对象，业务解析器又要求节点必须有 ID。[工具参数](../src/omp/flow-tool.ts#L100) · [对象构造](../src/omp/tools.ts#L47)

**建议与验收**　按节点种类和补丁动作声明字段，覆盖预设所需的 `workers`、`shards` 等参数。以 OMP 实际注册的 schema 为测试入口，至少验证线性派单、单节点 DAG、带 worker 的预设和运行中补丁均可进入处理器，缺少必要字段时返回对应字段的错误。

### 3. 指定历史任务 A 的补丁改到了正在运行的 B

同一目录下有历史 Flow A 和运行中的 DAG B。请求给 A 加节点，执行函数却返回 `patched: true, flowId: B`，新增节点实际进入了 B 的执行计划。目标查找只核对目录里存在 A 的检查点，应用补丁时使用了该目录当前运行的图。[目标查找](../src/omp/hub.ts#L277) · [补丁执行](../src/omp/flow-tool.ts#L293)

**建议与验收**　在真正修改图的位置同时核对请求的 Flow ID 和当前运行实例。用 A、B 重放此例，对 A 的请求应报告 A 当前不可修改，B 的图与检查点保持原值。随后对 B 发同一补丁，只有 B 新增一个节点。此项应与工具参数修复一起验收。

## 架构与恢复

### 4. 同一角色的阶段约束随派单写法改变

普通 `roles: ["algo"]` 调用旧的线性执行器，首次运行整个 `algo` 角色。等价单节点 DAG 则编译角色的 YAML 工作流，从 `algo__audit` 开始。另用声明“先人工确认、再工作”的临时角色复核，普通派单调用一次 worker 后就返回 `completed`。这使常用入口里的人工确认依赖模型主动提问。[执行器选择](../src/omp/workspace.ts#L296) · [线性执行器](../src/flow/orchestrator.ts#L219) · [内置算法角色](../roles/algo.yaml#L27)

**建议与验收**　保留简便的 `roles` 语法，统一两种入口对角色工作流的解释。用同一角色分别派单，核对两条路径的阶段、挂起位置、答复后的续跑位置和最终验收条件。用无工作流的 `dev → qa` 和已有线性检查点覆盖兼容性。

### 5. 界面显示可恢复，内部 DAG 仍停在 running

在临时 SQLite 中保存运行中 DAG 和已退出的属主 PID，重新创建工作区。监控状态变成 `interrupted`，持久化的状态机仍为 `running`。调用 `resumeManagedFlow` 后立即得到 `failed`，专员调度次数为零。恢复事件遇到 `running` 会直接返回。[检查点接管](../src/flow/state.ts#L187) · [状态机恢复](../src/flow/machine.ts#L78) · [宿主恢复入口](../src/omp/workspace.ts#L296)

**建议与验收**　接管租约时同步恢复内部节点状态，监控界面从恢复结果读取状态。用“一个节点已完成、一个节点执行中”的 DAG 模拟属主退出。新进程应保留前者的交接，重新派发后者一次，并能走到正常终态。

## 工作区、产物与验收证据

### 6. QA 可以给失败或过期的测试签发通过凭据

用 `bun test nested.test.ts 2>&1 | tee test.log` 保存日志时，测试输出为 `0 pass / 1 fail`，整条管道退出 0，插件仍生成了成功回执。另一例中，QA 第一轮测试通过后挂起，文件在期间发生变化，第二轮没有重测，却使用第一轮的工具调用 ID 给新工作树签发了 `ready`。实现会遍历复用会话的全部工具历史，并在交接时计算工作树指纹。[测试识别](../src/flow/evidence.ts#L36) · [历史调用收集](../src/omp/session.ts#L199) · [回执生成](../src/flow/evidence.ts#L113)

**建议与验收**　执行测试时记录测试进程退出码、调用 ID、所属阶段和受测版本。无法确定测试进程退出码时，将该次结果标为未验证。上述两个反例都应阻止 `ready`。在新工作树上成功重测后，回执应指向本次调用及其受测版本。

### 7. 预览分支拿到了主工作区的验证结果

主目录的 `check.txt` 内容为 `PASS`，专员在预览候选中改成了 `FAIL`。使用 `branch_preview` 合并后，门禁 `grep -qx PASS check.txt` 在主目录退出 0，Flow 返回 `completed`，交付分支里的内容仍为 `FAIL`。合并节点产生了引用，但下游门禁按上游 worktree 路径选目录，找不到时退回主目录。[预览分支生成](../src/flow/worktree.ts#L159) · [门禁目录选择](../src/flow/machine-helpers.ts#L150) · [命令执行](../src/flow/executor.ts#L346)

**建议与验收**　将合并得到的提交传给门禁，在该提交的隔离工作树内执行，并把提交 SHA 写入回执。用“主目录通过、候选失败”和“主目录失败、候选通过”两组相反样例验证，结果应只随候选变化。

### 8. 并行写任务可以完成，却没有可取回的产物

`fan_out_join` 允许省略 `merge`。两名专员在自动分配的 worktree 中各写出一个真实文件后，Flow 报告 `completed`。主目录中没有这两个文件，清理步骤也删除了对应的 worktree 和插件建立的 Git 引用。[预设构造](../src/flow/graph-presets.ts#L97) · [终态清理条件](../src/flow/machine-helpers.ts#L104) · [Git 清理](../src/flow/worktree.ts#L199)

**建议与验收**　在派单前为每个可写分支确定交付方式。缺少落地步骤时可拒绝计划，或显式交付预览引用。凡报告 `completed`，都应能在清理后从交付记录取回两个文件，并核对其内容。

### 9. 合并失败会改变用户正在编辑的文件和暂存区

专员工作期间，用户修改同一行并暂存。插件在用户目录执行 `git apply --3way`，随后返回 `working-tree-drift` 并提供预览分支。此时用户文件中已经写入冲突标记，原本已暂存的条目变成了 `UU`。已有测试覆盖了两个专员之间的冲突，还需覆盖用户暂存区参与的冲突。[补丁落地](../src/flow/worktree.ts#L177) · [现有冲突测试](../test/unit/phase10-worktree-merge.test.ts#L115)

**建议与验收**　在隔离工作树和索引中预演合并，落地前复核用户工作区与索引是否仍匹配。对“派单后用户又暂存同一行”的案例，失败前后逐项比较文件字节、`git diff --cached` 和 `git status --porcelain`。三者应保持一致，预览分支仍可查看专员的结果。

## 建议实施顺序与验证范围

1. **先保护用户文件，让交付可取回、可复验。** 优先处理第 9、8、7、6 项，用真实 Git 和刻意失败的测试同时检查文件、暂存区、交付引用和验收回执。
2. **再修正常对话中的确认与派单。** 一起处理第 1、2、3 项。让相同的合法请求通过宿主参数校验，再验证实际修改的是用户指定的任务和节点。
3. **统一角色工作流与恢复。** 处理第 4、5 项后，从正式工具入口贯穿一次派单、人工挂起、重启、答复、继续执行和最终产物核验，并覆盖已有线性任务的恢复。

### 人工确认、通知与恢复

1. **查询进度仍可被当作批准。** 后台 `resume` 只传 Flow 和节点 ID 就会写入“已确认放行”。前台用户只问“现在进度如何”，模型连续提交两次 `ready` 摘要，两道人工关卡均被推进。建议让宿主把明确答复的原始用户消息绑定到 Flow、节点和当次提问。验收时，空答复、查询进度和重复投递均应保持挂起，明确批准只能推进对应关卡一次。[后台状态机](../src/flow/machine.ts#L105) · [前台推进](../src/omp/workflow-fg.ts#L118)
2. **角色内部同时提问时，用户无法指定要回答哪一问。** 传外层角色节点只能定位到子工作流，传内层节点 ID 又被顶层校验拒绝。建议在提问、展示和恢复入口共用稳定的嵌套节点路径。验收时让同一角色同时询问 A、B，分别答复后检查两份原文、两次状态变化及最终续跑结果。[工具校验](../src/omp/flow-tool.ts#L246) · [子工作流恢复](../src/flow/executor.ts#L190)
3. **连续两道人工关卡只通知第一道。** 两次挂起之间没有新增专员阶段，唤醒去重键相同，总控收不到第二个问题。建议按节点和本次挂起标识去重。验收时每个新问题触发一次通知，重复投递同一次挂起仍只通知一次。[唤醒标识](../src/omp/hub.ts#L97) · [通知触发](../src/omp/hub.ts#L203)
4. **有更新的检查点时，较早的失主任务无法按 ID 恢复。** 在同一 SQLite 中保留两项任务，较早一项的属主已退出，监控仍显示 `running`、不可恢复。建议按目标 Flow 检查租约并接管。验收时恢复较早任务，只重派其中被中断的节点，另一个任务的状态和租约保持原值。[检查点选择](../src/flow/state.ts#L170) · [按 ID 恢复](../src/omp/flow-tool.ts#L233)
5. **全图等待答复时，中断的并行专员没有续跑。** 并行启动 planner 与人工节点，在 `whole_flow` 挂起时 planner 被取消，检查点仍记为 `running`。答复后 Flow 转为 `failed`，planner 总共只被调用一次。建议在写入挂起检查点前标识已中断的兄弟节点。验收时只重派这些节点一次，保留已完成交接，并核对监控、检查点和最终产物。[取消执行](../src/flow/executor.ts#L414) · [恢复节点选择](../src/flow/machine.ts#L95)

### 产物、测试与交付版本

1. **只交清单就能满足角色的最终验收。** 角色声明 `out/final.txt`，末阶段声明 `out/manifest.txt`。只创建清单，实际产物验证器仍允许 Flow 完成。建议在角色退出时同时验证两层约束。回归应覆盖只交清单、只交最终文件、两者均存在三种情况，只有最后一种能完成。[阶段权限与退出条件](../src/core/scope.ts#L238) · [角色最终交接](../src/flow/workflow.ts#L216)
2. **shell 退出 0 时，QA 仍可能为未执行或已失败的测试签发 `ready`。** 对已存在的文件运行 `test -f example.test.ts || bun test example.test.ts` 会跳过测试。运行 `bun test example.test.ts > suite.log 2>&1 && echo passed; echo finished` 时，失败写入日志，最后的 `echo` 成功。两例都取得了成功交接。建议收集本阶段实际测试进程的退出码、调用 ID 和受测版本，无法判定的命令应要求重测。验收时两例均应拒绝 `ready`，并保留直接运行成功测试的正例。[测试识别](../src/flow/evidence.ts#L62) · [回执签发](../src/flow/evidence.ts#L180)
3. **挂起期间移动预览分支，门禁会验证另一个提交。** 合并时的候选是 `FAIL`，挂起后将预览分支移到 `PASS`，恢复后 Flow 完成，回执指向新 SHA。建议把合并返回的 `mergedCommitSha` 持久化，并传给门禁和交付回执。验收时移动分支，原候选仍须失败，受测 SHA 与合并当时一致。[合并事件](../src/flow/executor.ts#L361) · [提交解析](../src/flow/worktree.ts#L252)
4. **三条并行路径在报告 `completed` 后丢失产物。** 预览合并后，可写的 `joinRole: dev` 写出的报告随临时工作树被删除。运行中通过补丁跳过唯一合并节点，已启动写分支的结果被清理。合并节点使用 `join: any` 时，慢分支的文件未进入交付。建议在图变更和终态清理前检查每个应交付的写节点是否已有可取回的结果，并让可写汇总节点提交自己的输出。验收时分别运行三例，在清理结束后按交付记录读取每个预期文件并比对内容。无法交付时不能报告完成。[汇总节点](../src/flow/executor.ts#L240) · [工作树清理](../src/flow/worktree.ts#L265) · [运行中补丁](../src/flow/graph.ts#L235) · [合并就绪条件](../src/flow/machine-helpers.ts#L173)

### 建议修复顺序

1. 先处理会造成错误批准、错误通过或静默丢失交付的问题。优先覆盖空答复与进度询问、QA 假通过、角色产物漏验、并行清理和子目录落地。每个反例配一个合法成功的对照。
2. 再贯通人工挂起与恢复。用同一组 Flow、节点和提问标识串起展示、通知、答复与检查点，并覆盖嵌套提问、连续提问、多个检查点及被中断的并行专员。
3. 固定预览提交，补齐脏工作区和分支冲突的回归。最后从正式 OMP 入口走一次“派单 → 挂起 → 重启 → 回答 → 清理后取回产物”，记录答复原文、受测 SHA 和交付文件内容，作为端到端验收。
