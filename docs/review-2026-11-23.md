## P1 · 优先修复任务控制与完成判定

| 问题与证据 | 建议修改 | 回归验收条件 |
| --- | --- | --- |
| **旧 Flow ID 命中新任务。** 同项目 A 等待输入时启动 B，查询 A 返回 B，取消 A 实际取消 B。历史检查点只定位到工作区，后续操作使用当前 room。[Hub 路由](../src/omp/hub.ts) · [工具入口](../src/omp/tools.ts) | 查询按指定 ID 读取记录。取消、留言、恢复均校验任务身份，无法控制该任务时明确返回原因。`/flow cancel` 与工具共用同一判断。 | A 等待、B 运行时，从工具和命令入口操作 A。查询应返回 A；对 A 的答复、恢复或取消均不能改变 B 的状态、留言或文件。 |
| **同项目可以同时出现两个执行者。** 两个独立的 room 连接同一数据库，后启动的实例仍能创建第二条 `running` 记录。文件变更可能被归到另一任务。[任务状态](../src/flow/state.ts) · [持久化](../src/core/store.ts) | 在数据库事务中按目标项目取得执行权，记录所有者并处理异常退出。启动和恢复共用此机制。 | 两个独立 OMP 进程同时向同一目录派单，最多一个进入执行。终止所有者后可恢复一次；不同项目仍能并行。 |
| **已接受取消仍会开始第一轮执行。** 用可控延迟模拟子会话创建，在创建期间取消。取消返回成功，之后 `prompt` 调用 1 次、`abort` 调用 0 次，最终记录为 `cancelled`。[取消入口](../src/flow/state.ts) · [子会话启动](../src/omp/session.ts) | 创建会话前后均检查取消状态，首次调用模型前再核对。已创建的会话要释放。 | 在创建前、创建中、首轮执行中分别取消。前两种情况不得执行首轮；后一种应向宿主发出中止，并记录实际结束状态。 |
| **未执行开发或测试也会完成。** `planner → dev → qa` 的 planner 首轮返回 `rejected`，仅 planner 执行，Flow 与 mandate 均记为 `completed`。[编排器](../src/flow/orchestrator.ts) | 在整条链确为只读审计时，允许“审计结束且发现问题”。有待执行的交付阶段时，保留拒绝原因并进入可处理的阻塞或返修状态。 | 同时测试单 reviewer 的负面审计结论，以及上述混合角色链。前者可完成审计；后者不得完成开发任务，Flow 与 mandate 状态须一致。 |
| **后台命令可能运行却没有任务记录。** 临时项目使用失效的 `mandateId`，登记报 SQLite 外键错误；命令随后写出了标记文件，任务表仍为 0 行。[后台启动与登记](../src/jobs/runner.ts) | 先校验关联并登记启动意图，确保登记成功后才放行命令。对登记后启动失败也保留可查询结果。 | 分别注入数据库登记失败和进程启动失败。前者无命令副作用，后者可查失败原因；重试后只有一次实际执行。 |
| **跨项目使用了发起方的信任状态。** 代码审查发现，从 A 派单到 B 时，目标角色与设置加载使用 A 的宿主上下文，B 的项目级配置可覆盖内置角色。[目标解析](../src/omp/hub.ts) · [配置刷新](../src/omp/workspace.ts) | 按目标目录取得宿主信任判定。若宿主无法判定，先使用内置与全局配置，明确提示目标项目覆盖尚未启用。 | A 受信、B 待确认时，B 的项目角色与设置不生效；确认 B 后仅 B 的覆盖生效。重启后重新验证该行为。 |

## P2 · 提高交付证据和故障诊断的可信度

| 发现 | 建议与验收 |
| --- | --- |
| **`ready` 的门槛低于角色声明的交付要求。** 一行文件被引用到第 900 行也能保存为 `verifiedFacts`。内置 algo 只有一次成功读取、没有报告或指标，也能交接为 `ready`。[交接校验](../src/flow/handoff.ts) · [算法角色](../roles/algo.yaml) | 校验引用行确实存在，保留可复查的执行证据。给 QA 的测试执行、algo 的报告与指标增加可检查的退出条件；缺件时说明缺什么。`needs_input` 应能在材料未齐时正常挂起。 |
| **保护范围与 README 的“物理锁死”表述有差距。** QA 的文件编辑有路径限制，部分执行产生的写入则靠阶段结束后的快照发现。大于 32 MiB 的文件用大小和修改时间标识，当前也存入 `sha256` 字段。[权限检查](../src/core/policy.ts) · [快照实现](../src/core/fs.ts) | 文档区分事前阻止与事后检测。需要保证源码全程只读时，用只读挂载或隔离工作区做验收。对需复现的模型或数据产物计算内容摘要，并把元数据指纹标为不同类型。 |
| **恢复失败会留下假的运行状态。** 挂起后移除自定义角色，再恢复会报 `Unknown role`，检查点已先进入 `running`。[恢复入口](../src/omp/workspace.ts) | 在进入运行态前验证角色和所需记录。删除角色后恢复应得到可诊断的失败，保留可重试的检查点；恢复角色后可继续，期间不占用执行权。 |
| **模型服务错误会被归为角色违规。** 用模拟宿主返回 `502 Bad Gateway`，阶段报告 `missing_handoff`，Flow 最终记录为 `violation`。[宿主适配](../src/omp/session.ts) · [错误归类](../src/flow/orchestrator.ts) | 保留可安全展示的宿主错误与阶段信息。分别测试服务失败、模型正常结束但未交接、真实越界三种情况，三者应产生可区分的结果。 |

## 下一次真机验收

在两个 OMP 窗口和两个临时项目中运行。先让项目一的 A 挂起，再在同项目启动 B，并让项目二的 C 并行执行。从另一窗口按 A 的 ID 查询、答复和请求恢复。B 占用执行权时应明确告知用户；B 释放后，A 从原阶段继续。最后核对三个 ID 各自的用户答复、阶段记录、数据库终态和文件变更，并在真实前台确认提问与完成通知是否送达。这样一次验收就能覆盖任务身份、同项目互斥和跨项目交互。
