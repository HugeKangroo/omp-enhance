## 状态一致性与恢复

- **P2 · 取消在前后台产生不同结果。** 同一个专员显式声明“拒绝 → 取消”。后台产生取消终态。前台提示已停止，却把任务留在原审批门。下一轮回答“同意”，同一任务返回 `nextPhaseId: publish`。本例测到阶段推进。建议前台向共享状态机提交用户决定，分别验证暂缓后可继续、取消后原任务结束。[前台分支](../src/omp/workflow-fg.ts#L113) · [状态机取消](../src/flow/machine.ts#L163)
- **P2 · 已完成项目重新出现在待答列表。** A、B 各等一个答复，第二个窗口完成 A，原窗口按 ID 查 A 已是 `completed`。原窗口回复仅剩的 B 时，却同时列出 A、B 两个等待候选。建议汇总时先按项目和 Flow ID 对齐持久状态，再使用本窗口快照补充，覆盖“另一窗口已完成”的用例。[候选汇总](../src/omp/hub-helpers.ts#L155)
- **P2 · 补丁回执可能早于可靠保存。** 在临时库只对含新增节点的检查点写入注入失败。追加 reviewer 返回 `patched: true`，另一个 SQLite 连接读到的任务图和运行状态均为旧版。正常对照中两处都含新节点。若下一次成功保存之前进程退出，确认过的改派将丢失。建议收到新的持久化版本后才确认，失败时报告可重试状态。此例验证了写入失败时的行为，未测量实际发生频率。[写入异常](../src/flow/state.ts#L140) · [成功回执](../src/flow/executor.ts#L339)
- **P2 · 已移除的角色能追加，却无法恢复。** Flow 启动时 A 在目录里，图尚未引用 A。移除 A 后，新 Flow 会拒绝点名 A；旧 Flow 追加“人工确认 → A”仍返回成功，挂起重开后却提示必须恢复该角色。建议新引用只选当前可用角色，已经引用的角色按明确的冻结或撤销策略处理，并在接收补丁和恢复时使用同一判断。[补丁角色目录](../src/flow/executor-gate.ts#L91) · [恢复校验](../src/omp/workspace.ts#L402)

## 怎样判断 Agent 的自主能力

**CI 评分仍会把好坏答案判反。** 同一个时区样例，写明“已排除连接池问题。根因是时区”并给出两处正确引用和双时区复验的回答被判失败。只说“排查材料包括 `src/settlement/window.ts:10` 和 `ci/failing-build-418.log:1`。日志使用 UTC。”却被判通过，连“有可执行下一步”也为真。拒绝词的匹配跨过了句子边界，文件名和 UTC 又同时充当了验证动作的关键词。建议独立判断因果结论、证据支持程度、复验动作，使用同一对正反例盲评校准。另将带 `enhance_flow` 的用户可见答复送入盲评导出，已有泄漏检测器能认出工具名，实际导出的候选仍保留它。应在真实导出边界执行检测，并单独保存原始答复。[矛盾规则](../scripts/eval-ci-diagnosis.ts#L116) · [评分项](../scripts/eval-ci-diagnosis.ts#L412) · [盲评导出](../scripts/eval-ci-diagnosis.ts#L472)

**新增自主组可以测试选路，但三道 CI 题都已替 Agent 定义了问题。** 提示明确指定目标日志、文件行号和复验方式；自主组让模型选择自己诊断或派单，而内置总控要求深度多文件审计交给专员。需要先明确该组究竟允许哪些选择，再拿它与固定编排比较。目前这些题不能回答用户更关心的“拿到模糊目标，Agent 能否自行设计验收”。[试题提示](../scripts/eval-ci-diagnosis.ts#L640) · [自主组指令](../scripts/eval-ci-diagnosis.ts#L757) · [总控角色](../roles/coordinator.yaml#L7)

建议沿用上轮的 3D 桌子试点。只给“把它摆到能直接导入引擎”，分别提供有陈设参考、用途确实不明、引擎不可用的环境。让 Agent 自己决定查什么、问什么、如何判定完成，保留当时提出的验收条件。评测者用目标引擎重导、检查姿态及尺寸，并给出倒扣但稳定的候选，检验 Agent 的标准能否识别错误。分开记录理解错用途、执行错姿态、判错成品以及如实报告待验的次数，再比较同预算下直接派单与先对齐需求的结果。此项属于下一轮评测设计。[上轮案例与验收](review-2026-11-27.md#从模糊意图到可验证的任务)

## 当前版本的产品点评

截至 `c4f9718`，它最适合让一个人同时跟进几个有明确交付物的项目。用户可以留在同一段对话，把执行、等待、恢复和取证交给系统。上轮 6 个 P1 和 4 个 P2 的原始场景已有回归覆盖，本轮 `bun run check` 通过 168 项测试、2,210 次断言。审批“否”、两支分别落地、无改动预览落地、双时区 QA，以及取消后按依赖恢复，均有对应的行为检查。[本版可靠性回归](../test/unit/phase17-review-2026-11-28.test.ts#L153)

**从设计和开发看**，通用总控负责澄清与派单，专业知识、工具和验收可以随项目扩展。这一分工值得保留。临时任务能先借用现有角色并附验收要求；相同职责反复出现后再设项目专员。后台专员也能按项目和角色授权接 MCP 工具。仿真试验已有真实 Python 求解和结果校验；测试中的计划、专员行为和新角色定义由测试代码给定。它说明系统能承载新的专业做法。要认定 Agent 能自行创造并持续改进一种做法，还需记录它如何发现缺口、试用候选、比较效果并决定复用。[跨领域试验](../test/unit/phase16-cross-domain-intent.test.ts#L390) · [后台工具接入](../src/omp/session.ts#L334)

**从使用者看**，最值得改的是最终答复能否直接回答“我可以拿它去用了吗”。本轮将“必须在目标引擎以默认变换重导成功”写进任务验收。固定行为的专员在真实交接中列出已读的几何预检报告、尚未完成的引擎重导和环境缺口，并提交 `ready`。没有配置引擎命令门禁时，执行器仍返回 `completed`。建议把用户要求的必验项关联到可重跑的检查或明确的人工验收。若有必验项待核实，交付时应直接告诉用户“几何预检已做，目标引擎导入待验”，同时保留已完成工作的证据。[必验命令与交接范围](../src/flow/handoff.ts#L142) · [范围记录](../src/flow/handoff.ts#L267)

**自然语言审批仍有实质风险。** 对“是否批准本次发布”，在同一等待状态下分别回复。“不能执行，预算没批。”保持等待，“同意”触发下游，符合预期。“方案可以，但这周别发”却也把审批标为成功并发出下游执行指令。此处测到状态机调度，未执行实际发布。建议将带有条件、推迟时间或更换审批人的答复保留为约束，只有对当下具体动作的明确同意才放行。[审批判断](../src/flow/human-policy.ts#L131) · [恢复与调度](../src/flow/machine.ts#L137)

**下一项产品验证**应跑完“问对问题 → 收到答复 → 按所选用途交付 → 使用端重验”。在五个桌子姿态样例中，现有用途不明题允许第一轮提问即得分。本轮用真实评分函数对照，正常询问用途能够通过；同一句问题后追加“已经按翻倒交付完成”并生成导入检查失败的候选，也判通过。建议分别回复“正常陈设”和“翻倒道具”，按两种用途验收最终产物。记录用户导入后是否需要手调、错误报完成的次数，以及专员交接是否减少了用户实际返工。已复跑三套基准自检和 OMP 宿主探针，3D 案例使用 JSON 几何和 Python 导入检查，本轮未做真实引擎导入或模型分组对照。[意图评分](../scripts/eval-ambiguous-intent.ts#L380) · [试验对话轮次](../scripts/eval-ambiguous-intent.ts#L623)
