# omp-enhance 使用体验与交付可靠性复核

2026-11-27 · 评审基线 `1b1816c`（`main`）· Bun 1.4.0 · OMP 19.2.1

最新提交的修复结果、仍存问题和适用范围见[6d59c16 修改与项目整体评估](#6d59c16-修改与项目整体评估)。下文原始记录保留了各问题首次出现时的版本。

## 项目点评

这个插件解决的是开发者同时盯几个项目时的协调成本。用户用 `/coord` 主动进入总控，说清目标，由总控派发专员，在需要决定时回到同一窗口。默认模式保留原生 OMP。此次在空项目用真实宿主执行 `/coord`、`/coord status`、`/flow status` 和 `/role list`，均得到预期响应，两个只读状态命令也没有创建任务数据库。这一入口值得保留。[使用说明](../README.md) · [命令入口](../src/omp/commands.ts#L118)

当前版本把角色的多个阶段展开到同一张任务图，专员、人工提问和验证步骤有独立的节点标识。新建任务中，并行问题可以分别回答，连续两次提问各自触发通知，暂停后可以重新派发被打断的专员。Git 预览门禁也会固定受测提交，指定子目录的派单可落到正确的包。此前的这些问题已有回归覆盖。[上轮复核](review-2026-11-26.md#修复后复核) · [本轮基线的回归用例](../test/unit/phase13-review-followup.test.ts)

日常使用中仍有三件事会损害信任：答复可能推进另一项任务，设置上的微小调整可能改掉实际执行步骤，完成通知也可能对应一份缺文件或漏报失败测试的交付。以下按用户遇到它们的时点列出重现结果和验收方法。

## 从用户操作出发的发现

### 1. 同一项目同时等两份答复时，可能答错任务

在同一项目依次挂起两件事。A 问“发票按月汇总吗？”，B 问“确定清理过期备份吗？”。两个节点都叫 `decide`。总控工具转交“发票按月汇总”时省略了可选的 `flowId`，系统挑了最近的 B。B 实际变为 `completed`，审批记录写入发票答复，A 仍在等待。显式指定 A 后，A 才收到答复。两项复现任务都只含人工节点，没有实际清理动作。[恢复目标选择](../src/omp/flow-tool.ts#L224)

**改进与验收**　把答复关联到当次展示的问题、任务和节点。若关联不唯一，像现有 `steer` 一样返回候选，由总控用目标和问题原文请用户选择。重放上述对话，选择前两项都保持等待，选择 A 后只推进 A，用户全程无需输入技术 ID。[已有歧义处理](../src/omp/flow-tool.ts#L174)

### 2. “可以说一下进度吗？”仍可能被当成批准

在前台专员的“是否批准进入交付？”关卡，分别输入四条消息，再让模型侧提交相同的 `ready` 交接。结果是“现在进度如何”保持挂起，“同意进入交付”正确推进，但“可以说一下进度吗？”和“先不要批准，我还要看材料”也推进了。确认词按子串匹配，关卡又接受未被识别为进度查询的非空回复。这个反例需要模型发起交接，不能据此推断普通聊天的误判频率。[用户话语判定](../src/omp/workflow-fg.ts#L10) · [前台关卡](../src/omp/workflow-fg.ts#L98)

**改进与验收**　区分收集信息和请求授权两类提问。授权关卡提供“同意 / 暂缓”明确选项，继续支持自然语言答复。查询、暂缓和歧义答复应能得到回复而保持挂起。以上四句作对照，再验证同一条批准消息最多推进一次。

### 3. 调整专员推理档位，会让原有工作流消失

用 `/role edit algo` 只把推理档位改成 `low`。改前同一派单首先调度 `algo__audit`，保存并重新加载后直接调度基础 `algo`。写出的全局覆盖文件丢失了五个阶段，包括指标确认。编辑器重建角色草稿时漏掉了 `workflow`。[角色草稿](../src/ui/role-studio.ts#L31) · [设置保存](../src/ui/role-studio.ts#L265)

**改进与验收**　编辑单一设置时保留完整角色定义，显示写入的是项目还是全局配置。修改档位并重载，逐项对比五个阶段、权限和退出条件，再实际派一次单，确认仍从审计开始、在指标确认处暂停。

### 4. 删除项目角色会一并删掉同名全局定义

在项目和全局各放一份同名但内容不同的自定义角色，打开标为 `[project]` 的定义，点击删除并确认一次，两份文件都消失。其他项目若使用全局定义也会受影响。确认框只写角色名，删除实现会遍历两个目录。[删除确认](../src/ui/role-studio.ts#L189) · [实际删除范围](../src/roles/loader.ts#L295)

**改进与验收**　操作绑定到选中的来源，确认框写明范围、路径和删除后的生效版本。删除项目覆盖后，在本项目应看到回退的全局角色，在另一项目仍能派发全局角色。

### 5. 第二个窗口会把正在运行的任务显示为空闲

两个独立插件实例打开同一临时项目，A 持有真实租约并在运行 planner。B 的 `/flow status` 正确显示任务 ID、目标和 `running`，但 `/coord status` 显示 `idle`，`/flow` 的面板渲染为“待命／空闲”。文本摘要读取了持久化记录，另两个入口读取观察窗口自己的内存状态。[文本摘要](../src/omp/hub.ts#L366) · [总控状态](../src/omp/commands.ts#L57) · [监控面板](../src/ui/flow-room.ts#L404)

**改进与验收**　三个入口共用一份只读任务快照，标明“在另一窗口运行”和最后更新时间。并列打开 A、B，在运行、等待答复和结束三个时点核对目标、状态和下一步，确认观察窗口始终不接管租约。

### 6. “派单前询问”在无界面的调用中直接启动

把 `flowRoutingMode` 设成 `ask`。有界面时拒绝确认，同一注册工具返回 `started: false`。用无界面的调用派同类任务，确认没有发生，任务已创建并运行到第一道人工关。对于从脚本使用同一配置的人，界面有无改变了设置的含义。[派单设置分支](../src/omp/flow-tool.ts#L388)

**改进与验收**　定义并展示 `ask` 的无界面行为。建议返回待确认的计划，让调用方能显式确认本次派单。无确认渠道时核对没有启动任务，带确认的正例应只启动一次。

## 交互改进顺序

1. **先让答复和设置只作用于用户选中的对象。** 总控提问时带上项目、任务目标和待决定事项。配置写入和删除时展示作用范围。优先补上第 1 至 4 项的对照用例。
2. **让看板先回答“我现在需要做什么”。** 首屏按待我答复、运行中、需介入、已完成排列。每条先展示目标和下一步。例如“账单服务 · 发票汇总｜等你选择按月或按周”，用户可以直接回“发票按月”。同名任务并存时再显示短标识，波次、节点和完整执行轨迹放在详情。
3. **让完成通知成为取回结果的入口。** 在同一条消息给出目标、交付位置和必验结果。有失败项就列出失败项和下一步。以清理后读到的文件、实际受测版本和退出码决定交付状态。并行写入、多项测试、迁移及补丁这几条路径应先有回归，再扩大自动派单使用范围。

## 验证边界

`bun run check` 通过类型检查、架构检查和 130 项测试，0 项失败。`bun run probe:phase0` 通过真实 OMP 19.2.1 SDK 与子会话生命周期检查。`bun run eval:ci-pilot --dry-run` 校验了 3 个样例、5 项评分检查。这三项是当前基线的结果。

上述补充场景另用注册的命令或工具、实际面板渲染函数、两个独立插件实例、临时 SQLite、真实 Git 和 Bun 测试复核。需要控制时序和角色行为时用了固定行为的专员替身。本次未运行真实模型的完整多项目对话，也没有真人可用性样本，不能从这些结果估计日常误派概率或平均完成时间。

## 定制能力与自主拆解

**设计判断。** 总控需要能根据目标、项目证据和执行反馈，自主决定直接做、拆给谁、何时调整。普通专员也需要能拆自己的工作、请求会诊或提出后续步骤。跨专员派发应有明确负责人，这样用户始终知道谁对整个任务及其验收负责。下文中的 Harness 指模型外的工具、权限校验、调度、持久化与验证代码，包含插件对 OMP 宿主能力的调用。

### 当前能定制到哪一层

| 用户意图 | 当前实现及边界 |

Agent 今天已经能调整自己的解题方法、复用现有角色，并为当前工作编写其写入范围内的脚本。项目里没有模型可调用的“生成角色或方法候选 → 试用 → 选定版本 → 保存为项目能力”流程。能写一份 YAML 或脚本草稿、把它注册成受管理的能力，以及让一个已挂起的任务续用某个确定版本，是三个分别需要验证的操作。

### 建议的用户体验和实施次序

用户说“把部分退款规则写给客服看，只改 `docs/refunds.md`，找另一个人核对”。已有能力足够处理这一单，总控可以选 `dev → reviewer`，把读者、范围和验收要求写进任务。若用户又要求撰写者全程禁用 Shell，单靠缩小文件范围达不到这个要求。此时应选符合约束的已有角色，或使用下述仅本次有效的受限角色。用户只需要看到做法、边界和交付物。

1. **先让已有角色能可靠地组合和复用。** 在派单时固定角色定义和图的版本，任务恢复、阶段展开、运行中追加均使用同一份已验证定义。验收用两个接同一角色的任务，一个挂起后配置改版，旧任务保留原方法，新任务采用新方法。追加的专员仍收到自己的具体简报，并经过声明的人工关卡。
2. **再支持 Agent 为自己或同伴生成任务内的角色和方法。** 优先查已有能力，确有缺口时才生成候选。角色从现有权限范围内选工具和写入路径，方法可以是操作步骤、脚本或评分器。让 Harness 在独立试跑中核对工具、产物和验收结果。支持“这次按这个办法做”。若用户说“以后这个项目都这样做”，显示变更内容和生效范围后保存新版本，再次开项目能复用，旧任务与其他项目保留各自定义。

### 先分开三个设计决定

用户从一个入口说目标，谁来决定下一步，以及谁用专业工具执行，可以分别设计。建议保留通用总控，把角色当作可以按项目扩展的职责。总控先看目标项目具有什么工具、能产出什么、怎样验收。领域知识足以决定下一步时，交给一个执行者；若拆解本身需要专业判断，允许领域专员制定技术路线，总控负责协调预算、依赖和用户决策。不同角色可以使用同一模型。

| 场景 | 起步方式 | 值得独立设专员或固定流程的时点 |
| --- | --- | --- |
| 影视剪辑 | 导演要求同一镜头早切六帧时，让一个能操作时间线的执行者保留素材和审美反馈。 | 多次交付中，画面剪辑和声音制作有不同工具、输入和独立验收时，再设剪辑与声音专员。锁定时间线后的多规格导出适合固定流程。 |
| 仿真操作 | 已有求解器、模型和边界条件，用户要扫一批参数，用操作方法、批处理脚本和结果检查即可。 | 换新模型、开发求解器或验证物理假设时，需要专门的技术规划和独立数值验证。执行者与验证者可以分开，双方交接模型版本、工况、单位和容差。 |
| 游戏开发 | 调角色手感时，让同一执行者围绕输入回放反复迭代。输入、摄像机和物理三个模块可能必须在同一帧对齐。 | 独立资产和玩法模块可以并行。每次构建的固定回放可自动回归，玩法是否有趣要用试玩反馈检验。 |

**判断顺序。** 如果差异只是知识或术语，先补项目说明或 Skill。如果差异是工具，先接工具并验证实际产物。只有当某项职责要长期复用，且有独立上下文、权限、模型需求或验收责任时，才固定为专员。一次性任务可以先用现有角色加任务简报和限制。步骤固定、验收明确的重复作业可以直接由 Flow 执行。这样既能持续增加角色，也能控制总控挑选角色的难度以及上下文交接成本。

**建议先试仿真操作。** 选一个已有可信基线的项目，把运行、产物读取和独立验证接起来。同批题目包括常规参数扫描、改变业务指标和更换物理模型，分别比较通用单执行者、总控咨询或派发专员、已有固定流程。共享工具、模型、预算、输入及评分标准，按任务类型报告正确率、返工、用户干预、等待时间，以及维护模板的成本。再用影视的同素材盲评、游戏的输入回放与盲试玩检查能否迁移。决定是否保留某个专员，应以它在哪类任务上带来了可重复的收益为据。

## 从模糊意图到可验证的任务

前面的派单评估从已有目标和验收条件开始。当用户只能说出想要的效果时，Agent 应能把它转成自己可以观察、执行和检验的问题，再决定是否拆给专员。现有任务简报可传入 `goal`、`constraints` 和 `acceptance`，执行器也能运行项目检查。上文的仿真算例由评测者给出容差，留下的产品问题是，换成用户的一句模糊请求，Agent 能否自己提出恰当的验收条件，并发现这些条件何时会误判。以下是设计建议和拟议验收用例。[任务简报入口](../src/omp/tools.ts#L89) · [执行门禁](../src/flow/executor.ts#L67)

### 什么时候追问，什么时候先做一个样例

Agent 可以先从用户将怎样使用产物入手，回答四个问题。用户最终要拿产物做什么？当前状态与目标差在哪里？有哪些可执行的调整？什么独立证据能说明差距缩小了？从项目设置、已有产物和约定中可以查出的信息，由 Agent 自己查。几种解释会交付明显不同的结果时，再借鉴 grill 式追问，每次只问一个能改变下一步决定的问题。低成本、可撤销的决定可以说明假设后先试。用户还没形成偏好时，可以给他看同一素材的两段十秒剪辑，请他指出哪一段的节奏更接近预期，把选择和理由用于下一版。

| 以“按视觉重力把这个 3D 模型摆好，让我能直接导入引擎”为例 | Agent 应建立的判断 |
| --- | --- |
| 确定使用目标 | 若资产是一张桌子，先查目标引擎的导入预设、项目里已验收的同类资产和使用场景。如果这张桌子用于正常陈设，预期是拖入场景时保留默认实例变换，桌面向上、桌脚着地，使用者无需再手动旋转、抬高或缩放。如果场景既容许正常陈设也容许翻倒的道具，问清用途再选择。 |
| 判断差异并尝试调整 | 保留原资产，记录比例与当前朝向，检查桌面、支撑脚相对地面的位置。在副本上尝试候选姿态，用相同视角比较调整前后，按项目尺度检查脚底间隙、穿地和尺寸变化。对称桌子可能有多个等价的水平朝向，应允许它们都通过。 |
| 检查验收条件本身 | 倒扣的桌子可能接触面积更大、重心更低，却无法按正常用途使用。用倒扣姿态挑战“越稳分数越高”的评分规则，再结合桌面用途和桌脚支撑判断。若用户指定翻倒道具，同一姿态应得到不同结论。 |
| 在使用端验收 | 将实际交付文件按项目预设重新导入目标引擎，以默认实例变换放入测试场景，复核朝向、着地和比例，保留场景截图及测量结果。只有建模工具的预览时，交付说明应标明“姿态已预检，目标引擎导入待验证”。 |

### 怎样用验证结果指导下一轮

模型负责解释意图、提出目标和评估办法、寻找能推翻自己判断的反例，并按证据修订方案。Harness 负责调用可用工具，保存原件、候选版本、导入设置和验证结果，让每条结论都能追溯到对应产物。几何与导入条件可用工具测量。审美与用途存在分歧时，把具体候选交给用户判断。上述步骤可由同一个 Agent 完成，有独立专业判断或工具需求时再分派。

复盘时要能分清三种返工原因。用户本想要翻倒道具，应修订目标。用户要正常陈设而桌脚仍穿地，应修正资产并重跑验证。倒扣桌子被评为优秀，应修订评分办法并回测旧案例。保留当时的目标、产物和判定依据，才能分辨下一轮究竟改善了什么。

**建议的首批验收用例。** 给 Agent 相同的自然语言请求，分别配上有明确陈设参考的项目、用途确实不明的场景、含倒扣候选的资产、以及缺少目标引擎的环境。依次观察它能否利用已有证据直接推进、只追问关键用途、拒绝几何分高但用途错误的结果、如实报告验证范围。再用对称资产检查是否误拒等价姿态。与直接派单的基线在同一批资产和预算下比较，优先记录导入后无需手调的比例、错误判为完成的次数，再看追问次数和返工耗时。引擎不可用的样例单列，避免混入导入成功率。
